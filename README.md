Ошибки, найденные в процессе разработки:

Двойной запуск таймера (Race Condition):

Проблема: Изначально ИИ сгенерировал логику, при которой можно было нажать «Старт» дважды, создав две активные записи для одного сотрудника.

Решение: Была добавлена серверная проверка в API (POST /api/time-entries), которая ищет существующую запись с endTime: null. Если она есть — возвращается ошибка 400. На фронтенде кнопка «Старт» блокируется, если в базе есть активная сессия.

Проблема часовых поясов (Timezone Bug):

Проблема: При выборе периода с помощью input type="date" записи за крайние дни (начало и конец периода) не попадали в отчет, так как время сохранялось в UTC, а фильтровалось по локальному времени.

Решение: В API-роуте GET /api/time-entries при помощи date-fns даты начала и конца периода были приведены к началу дня (startOfDay) и концу дня (endOfDay) в UTC.

Неверный расчет времени для активных таймеров:

Проблема: Если таймер запущен, но не остановлен, в отчете длительность показывалась как NaN или огромное отрицательное число.

Решение: В компоненте Reports добавлена проверка: если endTime === null, длительность рассчитывается как differenceInMinutes(new Date(), startTime) и помечается бейджем «В процессе».

**Коды ошибок:**

> `npx prisma db push` также заново перегенерирует клиент; отдельный `npx prisma generate` нужен только после правок `schema.prisma`.

## 🔍 Проверка кода на баги

Проверено скриптом на слое Prisma/SQLite (10 проверок, все пройдены):

### 1. Что будет, если остановить таймер дважды?
Было небезопасно: два параллельных `PATCH` читали `endTime === null` и оба записывали своё время — второй перезаписывал первое. Исправлено на атомарный условный апдейт:

```ts
const stopped = await prisma.timeEntry.updateMany({
  where: { id, endTime: null },
  data: { endTime: new Date() },
});
if (stopped.count === 0) return NextResponse.json({ error: "Таймер уже остановлен" }, { status: 400 });
```

Подтверждено тестом: из двух параллельных остановок ровно одна дала `count = 1`, вторая — `count = 0`, время остановки не перезаписано. Повторная остановка после завершения возвращает `400`.

### 2. Корректно ли SQLite сохраняет время в UTC?
Да. Prisma кладёт `DateTime` в SQLite как ISO-8601 строку с суффиксом `Z` (`2026-01-05T08:30:00.000Z`), при чтении получает обратно тот же момент времени независимо от локальной зоны (тест при `TZ = UTC+3`: round-trip точен до миллисекунд).

Следствие для фильтрации: границы периода на клиенте строятся из **локальных** дат (`YYYY-MM-DDT00:00:00` → ISO с правильным смещением), поэтому «Сегодня» включает локальную полночь, а не UTC. Запись в начале диапазона находится, за его пределами — нет (проверено).

### 3. Работает ли приложение после перезапуска сервера?
Да. `prisma/dev.db` — файл на диске, записи и `endTime` после рестарта читаются новым клиентом. Синглтон в `src/lib/prisma.ts` с кэшем на `globalThis` предотвращает накопление соединений при hot-reload в dev.

### Найдено и исправлено дополнительно
- **500 вместо 4xx на невалидный id**: Prisma бросает `PrismaClientKnownRequestError` при синтаксически неверном UUID — добавлена проверка формата (`400`) до запроса.
- **500 при несуществующем `employeeId`**: нарушался FK — добавлена проверка существования сотрудника (`404`).
- **500 при невалидном JSON в теле**: `req.json()` обёрнут в `catch`.
- **`as any` в GET-фильтре**: заменено на типизированные `Prisma.TimeEntryWhereInput` / `Prisma.DateTimeFilter`.

## 🐛 Ошибки, найденные при разработке

### 1. npm-кэш с битыми пакетами (Prisma 7 вместо 6)
`npm install` в среде с ограниченным доступом к registry дважды прерывался по таймауту. `package-lock.json` зафиксировал Next 16.4.3, Prisma 7.10.1 и Tailwind 4.3.3 вместо требуемых 14.2.15 / 6.14.0 / 3.4.17.

**Исправление:** зафиксированы точные версии в `package.json` (`"prisma": "6.14.0"`), удалён повреждённый `node_modules/.prisma` (остаток от Prisma 7) и битая запись `effect` без версии из lock-файла, затем `npm install` выполнен заново.

### 2. Повторная остановка таймера (гонка)
Два параллельных `PATCH` могли одновременно прочитать `endTime === null` и оба установить новое значение.

**Исправление:** `stop`-роут использует `updateMany({ where: { id, endTime: null }, data: { endTime: now } })`. Первый запрос обновляет 1 запись, второй — 0 (count = 0 → возвращает 400). Это атомарная «stop exactly once»-гарантия на уровне SQLite.

### 3. Часовые пояса при фильтрации дат
Клиент передавал `Date.toISOString()` (UTC), а фронтенд формировал `new Date(YYYY-MM-DD)` который интерпретировался как `00:00:00` локального времени — запись могла попасть или не попасть в диапазон в зависимости от смещения.

**Исправление:** в `Reports.tsx` дата-инпуты собираются в строки `${YYYY-MM-DD}T00:00:00` / `${YYYY-MM-DD}T23:59:59.999`, которые парсятся в `Date` напрямую. На бэкенде GET-роут принимает ISO-строки из URL, создаёт `new Date()` — они автоматически трактуются как UTC, что соответствует тому, как SQLite хранит `DateTime` (ISO-8601 UTC).

### 4. Несуществующий employeeId → 500 из-за FK
POST в `/api/time-entries` с несуществующим `employeeId` вызывал ошибку ограничения внешнего ключа в SQLite (500).

**Исправление:** добавлена проверка `employee.findUnique()` до создания записи; при отсутствии возвращается 404 «Сотрудник не найден».

1. Добавьте сотрудника (левая колонка).

3. Введите задачу, нажмите «Старт».

### Проверка повторного запуска таймера (guard)
1. Запустите таймер для сотрудника.
2. Не останавливая, попробуйте запустить снова (через API или повторным кликом).
3. **Ожидаемый результат:** сервер возвращает `400 «У сотрудника уже запущен таймер»`, кнопка «Старт» остаётся неактивной, вместо неё — «Остановить».

### Проверка двойной остановки
1. Запустите и остановите таймер.
2. Попробуйте остановить ещё раз.
3. **Ожидаемый результат:** `400 «Таймер уже остановлен»`.

### Проверка сохранения после перезапуска
1. Создайте и остановите запись.
2. Перезапустите `npm run dev`.
3. Откройте отчёт за день создания.
4. **Ожидаемый результат:** запись и время остановки сохранились.

### Проверка UTC-сохранения
1. Запустите таймер → остановите.
2. В отчёте проверьте, что «Начало» и «Конец» — корректные ISO-даты.
3. **Ожидаемый результат:** `startTime` и `endTime` сохраняются как `YYYY-MM-DDTHH:mm:ss.sssZ`.
